# Payment and vault hardening — 24 October 2026

The council review exposed real legacy issues. This release serializes payment completion and subscription activation in a service-only SQL transaction, preserves PAID against later updates, and prevents provider-payment reuse across orders. Browser reconciliation validates provider amount/currency. The webhook verifies the original body signature, rejects timestamps outside five minutes, ignores non-success attempt events, and never marks amount mismatches FAILED. Cashfree guidance: https://www.cashfree.com/docs/payments/online/webhooks/webhook-indempotency and https://www.cashfree.com/docs/api-reference/webhooks/reliability-and-operations . A provider-signed real/sandbox payment delivery was not exercised; tests use injected transport and isolated database fixtures.

Vault access: active firm SuperAdmin/Admin can manage; Staff can list/read/reveal/launch only credentials explicitly assigned to their user ID. Client and platform GodAdmin roles cannot use the vault. Filing metadata changes require a manager. Client links are saved and checked. get/list use safe response fields. Mutations check write results. An audit intent must persist before any write; a completion audit is then attempted. If the completion log fails, the durable intent remains and the request returns an error (the earlier write may already have committed). Reveal returns no plaintext unless its audit succeeds. New reveal requests require a reason of at least ten characters and signed authentication-method evidence from a sign-in in the last five minutes; a token refresh alone does not qualify. Frontend callers must supply the reason; there is no password-reveal control currently exposed in ClientProfile.

The deployed Supabase function had previously diverged from Git. It is now reconciled into a typed handler, policy and crypto implementation. Deno entry points are checked separately from the Vite TypeScript project. The Supabase SDK import is pinned. CI runs TypeScript/build, unit tests, Deno checks/handler tests and the Python worker tests; SQL tests remain isolated-preview-only.

Encryption uses a random IV plus authenticated data containing firm, client, credential and field. New ciphertext identifies its format/key version. The existing PORTAL_MASTER_KEY remains in place; this release does not rotate it. PORTAL_MASTER_KEY_VERSION defaults to 1. To rotate later, keep old version keys in the server-only PORTAL_PREVIOUS_KEYS JSON map and place the original legacy key under legacy if legacy payloads exist. Unknown versions or moved ciphertext fail to decrypt. Test rotation and recovery before changing production keys. Envelope encryption through an external KMS remains a future infrastructure option.

CORS accepts https://caath.in and https://www.caath.in plus exact comma-separated PORTAL_ALLOWED_ORIGINS. Add the exact preview origin if browser testing needs it. Calls without Origin still require verified authentication and authorization. No wildcard CORS is used by the vault.

Atomic rate counters are service-only; the browser cannot invoke the payment-completion or counter RPCs. Fixed-window counters are retained for operational review; schedule retention cleanup separately if their volume warrants it.

Validation includes full preflight, notice/GST/import/payment/crypto unit tests, role/assignment/reauth/audit-failure handler tests, isolated payment SQL retry/protection/privilege tests, a real concurrent-counter check, and real HTTP preview create/get/reveal/date-denial/cleanup tests using synthetic data. No production credentials were decrypted or payment transaction initiated. Existing unrelated public security-definer advisor findings remain for separate review. This is not a claim of complete-product security certification.
